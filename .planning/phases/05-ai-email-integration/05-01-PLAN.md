**Part A: packages/backend/src/services/email/index.ts** — Add enqueue step

In the `pollInbox()` function inside `createEmailModule`, add a new step after the audit log write (step h) and before `upsertLastUid` (step i). This step enqueues an AI draft generation BullMQ job for guest emails only.

Add this logic between the existing audit log write and `upsertLastUid`:

```
// j. Enqueue AI draft generation for guest emails
if (classification.category === 'guest_inquiry' && guestId) {
  try {
    const aiDraftQueue = app.queues?.getQueue(QUEUE_NAMES.AI_DRAFT);
    if (aiDraftQueue) {
      const guest = await app.prisma.guest.findUnique({
        where: { id: guestId },
        select: { language: true },
      });
      const guestLanguage = (guest?.language === 'de' ? 'de' : 'en') as 'en' | 'de';

      await aiDraftQueue.add('ai-draft', {
        conversationId,
        messageId: message.id,
        guestLanguage,
      } satisfies AiDraftJobData);

      app.log.info(
        { conversationId, messageId: message.id, guestLanguage },
        'AI draft job enqueued',
      );
    }
  } catch (draftErr) {
    // Draft enqueueing failure must NOT block email processing
    app.log.warn({ error: draftErr, conversationId }, 'Failed to enqueue AI draft job');
  }
}
```

Import `AiDraftJobData` from `@pyr/shared` at the top of the file (it's already exported from the shared package alongside QUEUE_NAMES).

Key rules:
- ONLY enqueue for `guest_inquiry` classification -- NOT for `ota_notification`, `spam_newsletter`, or `admin_system`
- ONLY enqueue when there's a `guestId` (non-guest emails don't get drafts)
- Wrap in try/catch so enqueueing failure never blocks email processing
- Read guest language from the guest profile at enqueue time (default to 'en')
- The ai-draft queue is already registered in Phase 1 with 3 retries and exponential backoff from 3s
- Use `app.queues?.getQueue()` with optional chaining because queues may not exist in test environment (NODE_ENV=test)

**Part B: packages/backend/src/services/queue/jobs/ai-draft.job.ts** — Fix dedup to per-message scope

The existing dedup query filters by `{ conversationId, status: 'pending' }`. This is wrong: CONTEXT.md says "Every inbound message in a thread gets a fresh draft." If message 2 arrives while message 1's draft is still pending, the dedup would skip message 2's draft.

Change the dedup query from:
```typescript
const existingDraft = await app.prisma.aiDraft.findFirst({
  where: {
    conversationId,
    status: 'pending',
  },
});
```

To:
```typescript
const existingDraft = await app.prisma.aiDraft.findFirst({
  where: {
    conversationId,
    messageId,
    status: { in: ['pending', 'failed'] },
  },
});
```

This ensures:
- Each message gets its own draft (dedup scoped to messageId, not conversation)
- A message with a failed draft won't get a duplicate if retried via the Retry button (which uses regenerate, not re-enqueue)
- Two different messages in the same conversation each generate separate drafts

Also update the log message from `'Pending draft already exists, skipping'` to `'Draft already exists for this message, skipping'`.

**Part C: packages/backend/src/services/queue/jobs/ai-draft.job.ts** — Add onFailed handler

The job processor function returned by `createAiDraftProcessor` only handles the success path. When BullMQ exhausts all retries (3 attempts), there is no signal to the frontend that generation failed.

Export a second function `createAiDraftFailedHandler` from the same file:

```typescript
export function createAiDraftFailedHandler(app: FastifyInstance) {
  return async (job: Job<AiDraftJobData> | undefined, error: Error): Promise<void> => {
    if (!job) {
      app.log.error({ error }, 'AI draft job failed with no job reference');
      return;
    }

    const { conversationId, messageId } = job.data;
    const logger = app.log.child({ jobId: job.id, conversationId });

    logger.error({ error: error.message, messageId }, 'AI draft generation failed after all retries');

    try {
      // Write a failed draft record so the frontend can detect and show the failure notice
      await app.prisma.aiDraft.create({
        data: {
          conversationId,
          messageId: messageId ?? null,
          content: '',
          status: 'failed',
          model: 'none',
          tokensUsed: 0,
          inputTokens: 0,
          outputTokens: 0,
          costEur: 0,
        },
      });
      logger.info('Failed draft record created for frontend detection');
    } catch (dbErr) {
      logger.error({ error: dbErr }, 'Could not write failed draft record');
    }
  };
}
```

This handler must be registered with the BullMQ Worker's `failed` event in the queue setup code. Add a note: wherever the ai-draft Worker is created (likely in `packages/backend/src/services/queue/index.ts` or similar), register:
```typescript
worker.on('failed', createAiDraftFailedHandler(app));
```

If the Worker creation is in the same file or a setup file, add the import and event registration there. If the queue setup uses a generic pattern that doesn't support per-queue failed handlers, add the handler registration in the queue module initialization.
